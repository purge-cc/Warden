# 0.43.0

## Coming from 0.41.0

If you upgrade from 0.41.0, everything in 0.42.0 is new to you too: Warden
Nodes (beta), the reworked terminal UI, and the new operator rules with
configuration schema 5. Read the [0.42.0 notes](0.42.0.md) for those
changes. The notes below cover what is new since 0.42.0, and how the
upgrade from 0.41.0 works now.

## Upgrading

Upgrade an existing install with the installer's upgrade mode:

```bash
curl -fsSL https://get.purge.cc | sudo sh -s -- --upgrade
```

or `sudo ./scripts/install.sh --upgrade` from an unpacked bundle or a
checkout. Without `--upgrade` the installer refuses a host that already has
Warden and tells you to rerun it with the flag.

0.41.0 keeps its configuration at schema 4, and 0.43.0 needs schema 5. The
upgrade now migrates the configuration inside its own transaction, so the
manual `warden migrate v4-to-v5` step that the 0.42.0 notes asked for is not
needed on this path. In order, the upgrade:

- checks the configuration with the new binary, before it changes anything;
- stops the daemon and the scheduled backup, and keeps the old binary and
  service unit;
- plans and applies the migration;
- installs the new binary and unit, starts them, and checks that the new
  daemon answers and blocks;
- only then finalizes the migration.

If the check finds something that blocks the migration, the upgrade stops
before it changes anything and prints the command that lists the findings. A
failure, or a Ctrl-C, a hangup or a plain `kill` (SIGTERM) before the final
step, rolls the configuration back and starts 0.41.0 again. The migration
moves the allow and deny rules you added in 0.41.0 into Custom Lists. The
old allow and deny commands now refuse to write: create a Custom List with
`warden custom-list` and mount it on a profile with `warden profile mount`.

The health check expects the new daemon to answer on the loopback address,
resolve one name and block another with a `0.0.0.0` answer. If your setup
answers blocked names in another way, or blocks everything, read "How the
upgrade runs" in `docs/UPGRADE_RECOVERY.md` before you upgrade. An upgrade
that fails the check rolls back.

If the upgrade ends with exit status 75 (most of these messages say
`RECOVERY REQUIRED`), or was stopped by a crash or a power loss, follow
`docs/UPGRADE_RECOVERY.md`. It ships in the bundle as
`docs/UPGRADE_RECOVERY.md`, under `/usr/local/lib/purge-warden/docs/` for a
get.purge.cc install. Some installer messages name the section to read;
otherwise start at "End states after exit 75", or at "Killed or crashed
upgrades" after a crash or power loss. The manual `warden migrate v4-to-v5`
commands are described there as a recovery tool, not as an upgrade step. A
file left with the `.s6-old` suffix by a killed upgrade makes the next
upgrade refuse before it changes anything, with the steps to recover.

Also in the upgrade:

- A host already on 0.42.0 has schema 5, so the upgrade runs no migration.
  It replaces the binary and the units.
- `--upgrade` no longer needs a LAN range (`--lan-cidr`), and its plan no
  longer lists the settings that only a fresh install uses (LAN range,
  listen address, upstream, lists, run user).
- Starting 0.43.0 on a schema 4 configuration, or running
  `warden config lint` on one, now says that `install.sh --upgrade`
  migrates it.
- If a signal stops the installer after the upgrade has committed, it says
  so and exits with status 4. The new version is installed and running; run
  the same command again to finish the remaining steps.
- The upgrade keeps your configuration where it is. A host installed before
  0.43.0 keeps `/var/lib/purge-warden/config.toml`; see
  [Configuration under /etc/purge-warden](#configuration-under-etcpurge-warden).
- On such a host the installer prepares the `backups` directory as the
  `purge-warden` user. A `backups` directory that is a symbolic link is
  left as it is, with a warning.

## Before you downgrade

- Open the dashboard once (`warden dashboard`). If it shows Policy recovery,
  press `r` (Recover) until the change is committed or aborted. The 0.42.0
  dashboard cannot read the recovery record that 0.43.0 writes for an
  interrupted batch of Query Log rules.
- If you moved the configuration with `warden config relocate`, move it back
  first with `config relocate --reverse`, run the same way as the move (see
  below). Releases before 0.43.0 do not know the move.
- 0.41.0 cannot read a schema 5 configuration. Once the upgrade has
  finalized the migration, a 0.41.0 binary cannot start on it.

## Query Log: hold rules, apply them together

In the Query Log, Enter on a row opens the rule dialog. Its Hold rule button
now holds an ALLOW or DENY rule for that domain on the Custom Lists you
pick, instead of opening a plan for that one domain. A "HELD RULES — NOT
ACTIVE YET" card shows how many rules are waiting. You can hold up to 32
rule-and-list pairs at a time, fewer if the daemon allows fewer, for one or
more domains, on the same list or on different lists.

Press `v` to review them. The held rules are a table with ACTION, DOMAIN and
LIST columns: ←/→ pick a cell, and `e` or a click on the selected cell edits
the action, the domain or the lists. An edit is checked like a new hold, and
Esc drops it. Delete or Remove takes one rule out, Discard all drops them
all after you confirm, and Review all shows a single plan. Apply saves every
held rule as one change with one reload, instead of one apply per domain.

Held rules do nothing until you apply them, and they live only in the open
dashboard session: quitting discards them, after asking first. An Apply
already submitted may still complete; the next `warden dashboard` shows its
outcome. If an apply fails or is cancelled, every held rule stays held.
Creating a New List from the picker is still a separate change with its own
plan and Apply. On a read-only node, apply rules on the primary.

## Configuration under /etc/purge-warden

A fresh install, from the installer or from `warden init` without
`--config`, now creates the configuration at
`/etc/purge-warden/config.toml`. The files it includes, such as Custom List
packs and list files imported from this machine, sit beside it. Downloaded
list caches, data and node state stay under `/var/lib/purge-warden`, and the
new configuration sets
`[backup] dir = "/var/lib/purge-warden/backups"` for backup archives.

An existing host keeps `/var/lib/purge-warden/config.toml`, and no second
configuration is created. `warden init` refuses to create one under `/etc`
while the old one exists.

## Moving an existing configuration: warden config relocate

`warden config relocate` moves the configuration of a host installed before
0.43.0 from `/var/lib/purge-warden` to `/etc/purge-warden`. Moving is
optional, and the upgrade never does it for you.

- It runs offline and as root. Stop `purge-warden` and
  `purge-warden-backup.timer` first, and run the real binary,
  `/usr/local/libexec/purge-warden/warden`. The `warden` command on your
  `PATH` runs as the service user, which the move refuses. `--config` is
  refused too: the two paths are fixed.
- Run `warden config backup` first. The move also refuses a configuration
  without an absolute `[backup] dir`.
- `--dry-run` runs every check and prints the plan, and moves nothing.
- Every file moves by rename, so it keeps its owner and mode. `/etc` and
  `/var/lib/purge-warden` must be on the same filesystem and mount;
  otherwise the move refuses and changes nothing.
- Node identity and cluster pairing survive the move. List files imported
  from this machine move with the configuration; downloaded list caches,
  state and backup archives stay in `/var/lib/purge-warden`.
- When `restorecon` is installed, the move relabels the new location.
- A run that stops part way prints the one command that rolls it back, and
  the daemon refuses to start until that command has run.
- `--reverse` moves the configuration back to `/var/lib/purge-warden`.

After the move, start `purge-warden` and the backup timer again, and wait
until `warden status` answers. `warden config relocate --help` lists the
exit codes.

## Rewrite and negative answers

A rewritten answer that holds records starts with a CNAME from the name the
client asked for to the rewrite target. Two things change:

- The CNAME always names the target you configured, the one policy checked.
  Before, it took the name from the first upstream record. Fresh, cached and
  stale answers behave the same.
- A rewrite whose upstream chain leads back to the name the client asked for
  is refused and answered as blocked. The rewrite step also counts toward
  the CNAME chain limit, `[cache] cname_max_depth`.

An NXDOMAIN answer whose upstream answer holds CNAME records now keeps them,
with the NXDOMAIN code and an SOA record. Before, the answer section was
emptied. For a rewrite, the CNAME from the asked name to the target is kept
too. An NXDOMAIN or NODATA answer with no records still has an empty answer
section, with no rewrite CNAME.

## Nodes

On a primary, a change that touches only policy now applies without
rebuilding the list corpus. This holds when the lists are unchanged and IP
blocklists are off before and after the change. Turning IP blocklists on or
off, or changing a list, still rebuilds. If the commit fails after the new
policy is swapped in, the change is not reported as applied.

## Backups

- On a node whose configuration is still under `/var/lib/purge-warden`,
  `warden config backup` refused list files that the node also hard-links
  into its list corpus. It now archives them, and still refuses any other
  hard link.
- On Fedora 44 every scheduled backup run failed with a `tar` error
  ("Function not implemented"). The backup unit now sets
  `RestrictSUIDSGID=no`, which this needs; the daemon unit keeps
  `RestrictSUIDSGID=yes`. The upgrade installs the new backup unit.

## Service unit

`purge-warden.service` now sets `SuccessExitStatus=75` and
`RestartForceExitStatus=75`. Some Nodes operations end the daemon with exit
status 75 so that systemd starts a fresh one, and they check for both lines
before they act. The upgrade installs the new unit. If you run your own
copy of the unit, add both lines to it. A drop-in keeps them unless it
resets `SuccessExitStatus=` or `RestartForceExitStatus=`.

## Terminal UI

- The Dashboard's Block Rate bars use a low, mid, high and critical colour
  gradient, with a legend on the Block Rate subtitle band. The Resources card
  says "Lists RAM".
- A click outside an open menu closes it without applying anything. A click
  outside an overlay that holds no unsaved work, such as help, an
  information panel or the Query Log detail, closes it like Esc. A click
  outside a form, or anything else that holds unsaved work, does nothing;
  use its buttons. The welcome banner ignores outside clicks, and nothing
  closes while an action is still running.
- A double click on a table row acts as Enter. It opens the Device form in
  Network → Devices and the rule dialog in the Query Log.
- In the Device form, Owner, Type and Department are pickers once labels of
  that kind exist, and a click opens them, like Profile and Group. With no
  label of that kind they stay free text.
- Removing a global Local DNS record that matches subdomains asks you to
  type its domain. Typing `n`, as in `nas.lan`, used to cancel that
  confirmation. It is now a letter like any other; Esc still cancels.

## Fixes

- On a machine with no configuration, `warden init` no longer prints the
  "no config file found" warning that tells you to run `warden init`, so a
  fresh-install log no longer carries it. `warden completion` and
  `warden config render-default` no longer print it either.

## Packages

No `.deb` or `.rpm` package is published for 0.43.0. Install and upgrade
with the bundle installer, from get.purge.cc or `scripts/install.sh`. This
release has no upgrade path for a host installed from a package.
