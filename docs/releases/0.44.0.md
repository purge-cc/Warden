# 0.44.0

## Who should upgrade

Every host on 0.41.x, 0.42.0 or 0.43.0. 0.42.0 and 0.43.0 were
pre-releases, and get.purge.cc served 0.41.0 as its stable version, so most
hosts come straight from 0.41.0. If yours does, everything in 0.42.0 and
0.43.0 is new to you too: read the [0.42.0](0.42.0.md) and
[0.43.0](0.43.0.md) notes first. The notes below cover what changed since
0.43.0 and what a 0.41.0 host must know before it upgrades.

Upgrade a 0.42.0 or 0.43.0 host soon if Warden's files are on btrfs, or on
another filesystem that can renumber its device at boot (ZFS, NFS, overlayfs,
device-mapper). On those hosts, a reboot after a policy change could stop the
daemon with `receipt identity mismatch` and leave DNS down. 0.44.0 no
longer compares the device number. A host already in that state can upgrade:
see [From a failed daemon](#from-a-failed-daemon).

## How to upgrade

Fetch the installer fresh and run its upgrade mode:

```bash
curl -fsSL https://get.purge.cc | sudo sh -s -- --upgrade
```

- Do not rerun a copy of `get.sh` saved from 0.41.0 or 0.42.0. The bundle
  ships `docs/UPGRADE_RECOVERY.md`, and those copies refuse it with
  `the bundle contains an unexpected path`. They install nothing.
- To preview the upgrade, add `--dry-run`:
  `curl -fsSL https://get.purge.cc | sudo sh -s -- --upgrade --dry-run`.
  The preview now changes nothing. Before, `--dry-run` on the command line
  replaced the installed bundle.
- From an unpacked bundle, run
  `sudo ./scripts/install.sh --upgrade --binary ./warden` in the bundle
  directory.
- Source installs: build with `cargo build --release`, then run
  `sudo ./scripts/install.sh --upgrade` from the checkout. `make install` is
  for a first install only and skips the configuration check. `make upgrade`
  from a 0.43.0 or older tree overwrites the `warden` wrapper and skips the
  check. The daemon kept running the old version. To fix such a host, run
  `sudo ./scripts/install.sh --upgrade` from the new tree; it upgrades the
  daemon and puts the wrapper back. `make upgrade` from the 0.44.0 tree
  refuses such a host and changes nothing.
- get.purge.cc publishes the bundle for x86_64 only. On aarch64, `get.sh`
  stops with `download failed` and points at building from source. Build as
  `BUILDING.md` describes, then run
  `sudo ./scripts/install.sh --upgrade --binary <path>` from the checkout, or
  `sudo ./scripts/install.sh --upgrade --build-from-source`.

The upgrade still runs as one transaction: it checks the configuration with
the new binary first, migrates a 0.41 configuration, starts the new version,
and checks that it answers and blocks. If a step fails, it puts the old
version back. If it ends with exit status 75 or `RECOVERY REQUIRED`, or a
crash or power loss stopped it, follow `docs/UPGRADE_RECOVERY.md`. The file
ships in the bundle, under `/usr/local/lib/purge-warden/docs/` for a
get.purge.cc install.

### From a failed daemon

On a 0.42.0 or 0.43.0 host, the upgrade now also accepts a daemon that
systemd reports as `failed`, so you can upgrade a host whose installed
version no longer starts. A 0.41.x host still needs a running daemon.

- `activating` means systemd is still retrying: wait until
  `systemctl is-active purge-warden.service` prints `active` or `failed`.
- `inactive` means the daemon was stopped: start it, then upgrade.
- A host that resolves names through its own Warden resolves nothing while
  the daemon is down, so the download fails. Add a temporary `nameserver`
  line to `/etc/resolv.conf` for the upgrade, and remove it afterwards.
- If the new version fails its check, the upgrade puts the old version back,
  starts it once and exits with `the exact old ELF and unit were restored`.

See "Upgrading a failed daemon" in `docs/UPGRADE_RECOVERY.md`.

### Cluster secondaries on 0.41

A 0.41 cluster secondary still cannot be upgraded in place. The upgrade
refuses it with nothing changed. Its `cluster_local_policy_conflict` finding,
listed by the command the upgrade prints
(`<candidate-elf> --config <master> migrate v4-to-v5 --check --json`), now
gives the steps. Take the node out of the cluster, upgrade both nodes, then
join again:

1. On the secondary, still on 0.41, run `warden cluster leave`. If it asks
   for a resolver, run `warden cluster leave --upstream <addr:port>`.
2. Upgrade the secondary as a standalone node.
3. Upgrade the primary.
4. On the primary, run
   `warden cluster create --migrate-legacy --san <primary address>`, then
   `warden cluster apply --preview-id <id>`, then
   `systemctl restart purge-warden`. If the primary's API is off or listens
   on loopback, add `--api-listen <addr:port>` with an address the secondary
   can reach.
5. On the primary, run `warden cluster invite`.
6. On the secondary, run
   `warden cluster join --peer <primary https origin> --invitation-file <file>`,
   then `warden cluster apply --preview-id <id>`, then restart it.

See "Cluster secondaries" in `docs/UPGRADE_RECOVERY.md`.

## Before you upgrade

- **Wildcard, regex and `$important` rules (0.41).** Configuration schema 5
  reads some of these rules differently. If the check finds one, the upgrade
  stops with nothing changed and prints the command that lists the findings.
  You can now accept them: list the findings with the command the upgrade
  prints (`<candidate-elf> --config <master> migrate v4-to-v5 --check --json`),
  write a choices file, and run the upgrade again with it:
  `curl -fsSL https://get.purge.cc | sudo WARDEN_UPGRADE_MIGRATION_CHOICES=/root/choices.json sh -s -- --upgrade`.
  Put the variable after `sudo`, not before it. A finding that allows only
  `defer` cannot be accepted. See "Migration findings" in
  `docs/UPGRADE_RECOVERY.md`.
- **IP blocklists.** If `[ip_blocklists]` is enabled, every source must be a
  public `https://` URL, with no user name or password and no private or
  loopback address. 0.41 skipped such sources with a warning, so they
  filtered nothing; 0.42.0 and 0.43.0 refused to start. `warden config lint`
  and the upgrade check now refuse them, and the upgrade stops with nothing
  changed. Change each such source to a public `https://` URL without a
  user name or password, or remove it, first.
- **Backups made by 0.41.** 0.44.0 restores only schema-5 archives. It
  refuses an archive from 0.41 or earlier with a message such as
  `schema-4 archive (Warden 0.41 or earlier); live config untouched` and
  explains how to copy its settings by hand. If you may need one of those
  archives, restore it before you upgrade. Run `warden config backup` once
  the upgrade is done.
- **Disk space.** Each policy write keeps undo data in the configuration
  directory for at least 24 hours. It is now capped at 2 GiB per
  configuration. A write that would pass the cap is refused with
  `UndoStoreFull` until older data expires. The REST API answers such a
  refusal with 429 instead of 503.
- **Anti-bypass** is now off by default. Up to 0.43.0 it was on by default
  but blocked nothing without `extra_domains`, so filtering does not change. A
  section that lists `extra_domains` keeps it on. `enabled = true` with no
  domains still warns. To stop the warning, list the resolver names to
  refuse in `extra_domains`, or set `enabled = false`.
  `warden lists add services/resolvers` adds a resolver list as an ordinary
  block list instead; it does not feed anti-bypass.

## Changes

### Upgrade and rollback

- The upgrade saves the publication store
  (`.warden-cluster-publications` in `/var/lib/purge-warden`) before the new
  version starts, and puts it back if the upgrade rolls back. It prints the
  copy as `publication store snapshot: <dir>`, under
  `/var/tmp/purge-warden-store.*`. On a node with the cluster enabled where
  the new version published a newer policy epoch, the upgrade does not put
  the store back: it exits 75 with `RECOVERY REQUIRED`, and you follow end
  state c in `docs/UPGRADE_RECOVERY.md`. See "Publication store snapshot"
  in `docs/UPGRADE_RECOVERY.md`.
- When the migration check blocks, the message now names
  `WARDEN_UPGRADE_MIGRATION_CHOICES` and the "Migration findings" section.
- A configuration with a `[[retired]]` entry dated in the past now upgrades.
  The check no longer reports the date as being in the future.
- `.s6-old` files left by a killed upgrade still make the next upgrade
  refuse with nothing changed. The steps it prints now include putting the
  publication store back.

### Start-up and reload

- `systemctl reload` during start-up no longer stops the daemon. A reload
  received while the daemon starts is applied once DNS serves. Before, it
  ended the process and systemd did not restart it.
- If the REST API certificate or key cannot be read at start, Warden logs
  the error and serves DNS with the REST API off, instead of restarting in a
  loop. A primary created with `warden cluster create` still refuses to
  start.
- Nodes start-up steps that fail, for example on a busy configuration lock
  or a damaged Nodes state, no longer stop a daemon that serves DNS. They are
  retried every 2 seconds and shown as `Problem:` lines in
  `warden node status` until they succeed.
- A Nodes listener that cannot be restored at start (address gone, port
  taken) is skipped and shown as a `Problem:` line in `warden node status`.
  DNS and the other listeners keep serving.
- `warden start --safe-mode` no longer exits when `config.toml` is invalid.
- A primary or standalone host now starts when a list has no downloaded copy
  yet (for example a list added while the daemon was stopped), or when its
  node-corpus bookkeeping fails. It logs the problem and serves DNS with the
  lists it has, instead of restarting in a loop.
- An IP blocklist source that cannot be fetched at start no longer keeps
  Warden in a restart loop. Warden logs a warning and starts with the IP
  lists it has. A cluster secondary, and every reload, still refuse a missing
  IP list.
- An unreachable IP blocklist source now fails after the 10-second connect
  timeout, instead of holding start or reload for up to 5 minutes.
- A node-corpus error during a reload, for example a list cache on another
  filesystem, now rejects the reload and keeps the current policy, instead
  of stopping the daemon. The rejected reload writes an audit record.
- A reload that changes only policy now reuses the loaded lists on a
  standalone host too, instead of downloading every source again. This holds
  while IP blocklists are off and the lists are unchanged.
- A reload where one domain list has no downloaded copy now applies with a
  warning and partial list coverage, instead of being rejected. A cluster
  secondary still rejects it.
- A standalone host no longer keeps the list corpus of every past policy.
  Old corpora under `/var/lib/purge-warden` are removed after each
  activation.
- Download files left by an interrupted list download are removed at the
  next start. A reload that rebuilds the lists removes those older than 20
  minutes.
- After a reload that rebuilds the lists, Warden keeps saving list state, and
  `warden status` keeps its counters current. On a node, a reload keeps each
  list's last refresh result.
- After a restart, `warden status` counts the lists loaded from their saved
  copy: `, N loaded from cache (next fetch pending)`. The Lists tab shows
  them as `cached`.
- If the daemon cannot finish an interrupted policy write at start, the
  error now names the `.warden-migration` fence, says not to delete it, and
  points to "Interrupted policy transactions" in
  `docs/UPGRADE_RECOVERY.md`.
- Saving `config.toml` in an editor with unchanged content no longer stops
  the daemon from recovering a policy write that was interrupted before it
  took effect.
- If Custom List rule recovery fails at start, the daemon retries it in the
  background. Rule changes return the cause and the next step instead of a
  bare 503.
- Journal lines now carry their real priority, so `journalctl -p err` shows
  Warden's errors.

### Restore and config

- `warden config restore` never changes cluster membership. It refuses an
  archive taken with another membership (for example while the node was a
  secondary, restored after it left) and leaves the live configuration
  unchanged. Use `warden cluster` to leave, join or create. After a
  membership change, run `warden config backup`: `--latest` is refused when
  the newest archive is older than the change.
- On a cluster secondary, `warden config restore` refuses to replace files
  the primary replicates. To restore a secondary: run `warden cluster leave`,
  apply and restart; restore an archive taken while the node was standalone;
  on the primary run `warden cluster revoke <node-id>` and
  `warden cluster invite`; then join, apply and restart.
  `warden cluster status` shows the node ID.
- A join that the primary refuses now names
  `warden cluster revoke <node-id>`: a node that left must be revoked on the
  primary before it joins again. With the daemon running, this hint is in
  the daemon log.
- When a restore or a cluster policy apply fails while it commits, Warden
  now rolls it back or finishes it at once, and says which. A restore it
  cannot settle names `systemctl restart purge-warden` and "Interrupted
  policy transactions", and never claims the configuration is unchanged.
- `warden config edit` now opens a private copy. The live configuration
  changes only if the copy is valid. If the copy is refused or the editor
  exits with an error, the live configuration stays unchanged, and the copy
  is kept and its path printed.
- `warden config edit` does not reload the daemon. Reload after a valid
  save: `warden config edit && sudo systemctl reload purge-warden`, or run
  `warden reload`. Some settings need a restart.
- A backup directory created by a root `warden config backup` now takes the
  owner of its parent directory, so the scheduled backup can still write to
  it.
- Config commands blocked by an interrupted policy write or v4-to-v5
  migration now name the step that clears it.
- Adding or editing list sources (CLI, REST or terminal UI) is now refused
  before anything is written when the daemon would reject the result, for
  example an unknown catalogue name or more than 64 sources. The REST API
  answers 400 instead of 500.
- A committed Custom List rule change now always activates, even while the
  daemon is busy with other rule requests.

### Policy and filtering

- Internationalised (IDN) names are handled in their `xn--` form. They now
  resolve under the default security checks, which refused every IDN query
  before. They match block and allow entries written as `xn--`, and they
  show as `xn--` in the Query Log and the CLI.
- A rewritten answer whose upstream response also has a CNAME for the
  original name (a conflict or a loop) is now blocked as malformed. Before,
  it was served next to Warden's rewrite CNAME.
- `blocklist add`, `lists add`, `blocklist set <id> url` and the Lists form
  in the terminal UI now refuse a URL the downloader would refuse:
  `http://`, a private or loopback address, or a user name and password. For
  a file on the host, the message names `warden blocklist import-local`.

### Nodes

- An Edit or Remove review that expires no longer blocks the node:
  `Review expired before apply; nothing changed. Prepare the operation again.`
- Adding a node no longer fails when a scheduled list refresh runs between
  review and apply.
- An Add can be cancelled until its destination applies it:
  `warden node cancel --operation-id ID --confirm`, or `c` in the Nodes
  recovery view.
- An Add on a primary that already serves a policy no longer restarts the
  primary because of a passing read error.
- `warden node token` no longer picks a loopback address by itself. When no
  reachable Nodes address is saved, pass `--listen IP:PORT`. A loopback
  address saved by an older `warden node token` is no longer offered to
  another host.
- Managed restarts now work on systemd older than 254, for example on
  Debian 12. A destination that does not run under the Warden systemd unit
  refuses an Add or Remove before it changes anything.
- `warden node status` and the Nodes view no longer re-hash the whole list
  corpus on every refresh.

### Terminal UI

- The header, menu gutters and footer use the theme's page background on
  every terminal palette.
- A double click on Choose in the restore picker no longer also confirms the
  restore on 24-row terminals.
- A policy preview applied after it expired, after a daemon restart or after
  a configuration change now returns to a fresh plan. It no longer locks
  policy edits in the terminal UI and `warden config relocate`.
- A profile save that the daemon refused, or made while it was stopped, no
  longer blocks later policy edits and `warden config relocate`.
- Capital letters and Shift symbols now type in the Nodes Add and Edit form.

### CLI

- `warden token regenerate` reloads the daemon, and the REST API then
  refuses the old token and accepts the new one. Before, the REST API kept
  the old token until a restart.
- `warden lists refresh` run while the daemon is stopped now updates the
  list cache that the next start serves. Run it as the service user; the
  hint names `warden --pid-file <path> lists refresh`.
- `warden lists forget` during a list refresh, and Custom List changes
  queued behind another change, now wait for the result instead of failing
  after 5 seconds.
- A command whose output is cut off, as in `warden config lint | head -1`,
  now exits 141 instead of aborting with a core dump.
- `warden firewall-rules` with a missing or broken configuration now prints
  the errors and exits 2. Before, it printed rules for the default port.
- `warden custom-list` and `warden profile mount` now exit 0 when the change
  is committed and applied. They exited 5 before.
- `warden blocklist remove` of an imported local list keeps its file and
  says so.
- `warden migrate v4-to-v5` with a `--config` path that does not exist now
  says `MasterNotFound` instead of naming a capability mismatch.
- `warden config relocate` refusals name `warden dashboard` instead of the
  `warden tui` command, which does not exist.
- The documented `warden config lint` exit codes are corrected: 0 for a valid
  configuration, with or without warnings; 2 for an error or a configuration
  that cannot load; 2 for warnings with `--strict`.

### Security

- The Nodes port now locks an address out for 5 minutes after 10 refused
  credentials (429 with `Retry-After`). It limits concurrent requests, and it
  checks credentials and association tokens before any configuration work.
  Hosts behind one NAT address share the count.
- `warden config restore` copies the archive privately before it reads it.
  It never restores archive owners, modes or set-id bits, and it refuses a
  symlinked archive, an archive over 1 GiB, and one with more than 10 000
  members.
- `warden stop --force`, and the reload after a restore, signal a process
  only after checking that it holds the daemon's PID-file lock and runs as
  the PID file's owner.
- `warden config edit` no longer writes through a configuration file that
  was replaced by a symbolic link during the edit.
- The cached list catalogue is read without following symbolic links, and
  at most 1 MiB of it.
- With the security checks off, an IDN query could skip a block entry
  written in `xn--` form. It now matches.
- Control and bidirectional characters in query data no longer reach the
  terminal. Queried names show such characters as escapes like `\033`.
  Other query data in the terminal UI, `warden logs`, `warden stats` and
  `warden status` shows them as U+FFFD.

### Dependencies

- anyhow 1.0.104 (RUSTSEC-2026-0190), event-listener 5.4.2
  (RUSTSEC-2026-0221) and chacha20 0.10.2 (the previous version was
  yanked).
- quinn-proto 0.11.19 (RUSTSEC-2026-0338 to RUSTSEC-2026-0342). It is built
  only with `--features doq`, which is off in a default build.
- lru 0.12.5 and paste 1.0.15 stay, through ratatui 0.29. Warden does not
  reach the affected code.

## Known limits

- After you renew the API certificate on a host whose Nodes address equals
  `api.listen`, peers cannot reach that host until you put the previous
  certificate back or move the Nodes address.
- A Nodes listener that could not be restored at start is not retried. Fix
  the cause, then restart the daemon.
- Nodes start-up problems show only in `warden node status`, not in
  `warden status`.
- A reload that changes a list, or any reload while IP blocklists are on,
  still rebuilds the lists.
- No `.deb` or `.rpm` package is published. Install and upgrade with the
  bundle installer.
- The installer and the upgrade check DNS on `127.0.0.1`. This fails on a
  host whose `listen` holds only a non-loopback address. A fresh install
  with such a `--listen` leaves a working daemon but exits with status 5.
  An upgrade puts the old version back after the 300-second health wait,
  unless you name the address:
  `curl -fsSL https://get.purge.cc | sudo WARDEN_UPGRADE_DNS_SERVER=<address> sh -s -- --upgrade`.
  The default listen, `0.0.0.0:53`, is not affected.

## Rollback

### Back to 0.43.0

After 0.44.0 has started once, 0.43.0 may not start on the same state
directory: it can restart in a loop with
`enrollment policy snapshot changed during publication`. A rollback by the
upgrade itself puts the saved publication store back first, except on a
cluster node where the new version published a newer policy epoch (exit 75,
end state c). After a killed upgrade or a `RECOVERY REQUIRED` exit, follow
"Killed or crashed upgrades" or "End states after exit 75" in
`docs/UPGRADE_RECOVERY.md`: they put the store back from the snapshot the
upgrade printed, before 0.43.0 starts. If
`warden config show --section cluster` shows `enabled = true`, first run the
epoch check in "Publication store snapshot". A completed upgrade deletes its
snapshot, so after a completed upgrade there is no supported way back to
0.43.0 on the same state directory.

### Back to 0.41.x

0.41.x cannot read a schema 5 configuration. A failed upgrade, or one
stopped by Ctrl-C, a hangup or SIGTERM before its last step, rolls the
configuration back and starts 0.41.x again. After a crash or a power loss,
follow "Killed or crashed upgrades" in `docs/UPGRADE_RECOVERY.md`. Once the
upgrade has finalized the migration, a 0.41.x binary cannot start on it.
