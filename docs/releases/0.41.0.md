# 0.41.0

## List refresh integrity

List updates now take a more deliberate path from download to the active
corpus. The aim is to keep a working list set available while an update is
being checked, and to refuse incomplete or inconsistent data before it can
replace that set.

### Refreshes publish as complete generations

Each configured source is resolved to one canonical identity before refresh.
Conflicting aliases are rejected during configuration checks and strict
startup. A reload that finds a conflict keeps the active configuration rather
than replacing it with an invalid one.

Cache data is admitted and published as a complete, validated generation, not
as a mixture of old and new source bodies. A refresh checks staged input before
it becomes active. If a refresh is refused or fails, an already accepted corpus
remains available instead of serving a partial update. Storage errors during
staging also prevent that generation from being published.

The refresh status distinguishes a degraded refresh from a healthy one and
keeps retrying within bounded work. Forced refresh requests for the same list
manager join existing work instead of starting competing writers.

### Lower-peak refresh path, with explicit limits

With a cache directory enabled, decoded HTTP data streams into a private
disk-backed generation. The parser and shard builder then work from staged
data, and publication waits for complete validation. This avoids retaining a
whole downloaded body and a whole replacement corpus on the normal refresh
path at the same time.

Input bodies, entries, parser lines, and format detection all have limits.
Size calculations fail safely on overflow, and staged content is checked again
before publication. URLs with embedded credentials are rejected before cache
metadata is accepted, while cache identity continues to use the exact resolved
URL.

This is bounded streaming, not a fixed process-memory promise. Peak memory
still depends on the installed domain set, configured limits, allocator
behavior, and operating-system cache. Running without a cache directory keeps
a supported, memory-resident fallback bounded by the configured body limit,
but it is not the lower-peak refresh mode.

### Safer configuration changes and recovery

Configuration writes are serialized so concurrent commands do not overwrite
one another. The configuration format upgrade is transactional and
crash-safe, with recovery controls for an interrupted change. Existing
configurations retain their active state if validation cannot complete.

### Dependency maintenance

The HTTP/2 implementation was updated to close RUSTSEC-2026-0258, which could
allow a peer to consume resources with an unbounded stream of empty DATA
frames.

Together, these changes make list refreshes easier to reason about: updates
become visible only as complete validated results, failures preserve the last
accepted data where available, and status reports show when refresh work needs
attention.
